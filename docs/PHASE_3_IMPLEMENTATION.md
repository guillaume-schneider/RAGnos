# Phase 3 Implementation Summary

Date: 2026-03-26

## Goal

Phase 3 focused on turning the local RAG stack into a more usable operator-facing product.

The main objectives were:

- make ingest incremental instead of full-rebuild-only
- support upload-driven onboarding and corpus updates in Chainlit
- append deterministic citations to answers
- add health and readiness tooling
- add a live eval runner and broaden regression coverage

This phase kept the same core stack and the same shared corpus model. It did not introduce multi-user document spaces, queues, or background workers.

## What Was Implemented

### 1. Incremental ingest with a manifest

Ingest is now incremental by default.

New implementation files:

- `src/ragnos/catalog.py`
- `src/ragnos/indexing.py`
- `src/ragnos/documents.py`

The system now tracks document-level state in:

- `chroma_data/manifest.json`

Each document record stores:

- relative file path
- content hash
- modification time
- page count
- generated chunk ids
- last indexed timestamp

Current ingest behavior:

1. scan the `documents/` directory
2. compute current per-file records
3. compare current files against the manifest
4. classify files as new, changed, unchanged, or deleted
5. upsert only new or changed PDFs
6. delete chunks for removed PDFs
7. update `manifest.json`
8. update `.fingerprint`

Fallback behavior:

- if the manifest is missing
- if the manifest is invalid
- if the Chroma store cannot be reopened cleanly

the system falls back to a full rebuild.

Deterministic chunk identifiers were also added so changed or deleted documents can be updated safely without rebuilding unrelated files.

### 2. Upload, refresh, and status flows in Chainlit

The application chat flow now supports operator actions directly in the UI.

Main implementation file:

- `src/ragnos/app.py`

Supported commands:

- `/upload`
- `/refresh`
- `/status`

Behavior added:

- if no usable corpus exists at startup, the app can ask for PDF uploads directly
- uploaded PDFs are saved into the shared `documents/` directory
- ingest is triggered immediately after upload
- the shared runtime state is invalidated after ingest and rebuilt against the new fingerprint
- `/refresh` forces a revalidation and re-open of the runtime state
- `/status` prints a concise readiness summary in chat

Upload policy updates:

- uploads are restricted to PDF files
- oversized or invalid uploads are rejected with explicit errors
- replacing a file with the same name updates that file in the shared corpus

Chainlit configuration was tightened in:

- `.chainlit/config.toml`

### 3. Deterministic citations appended to answers

Answers now include a deterministic `Sources:` section when retrieved chunks were used.

Main implementation file:

- `src/ragnos/runtime.py`

New behavior:

- citations are built from retrieved documents, not generated by the LLM
- citations include source filename and page number
- duplicate source/page pairs are collapsed
- the final rendered answer includes the answer text followed by a `Sources:` block
- cached answers preserve the exact rendered citation block

This means cache hits now return the same answer format as uncached responses, including citations.

### 4. Healthcheck support

Operator health tooling was added through:

- `src/ragnos/health.py`
- `src/ragnos/healthcheck.py`
- `healthcheck.py`

The healthcheck covers:

- prompt file validity
- documents directory presence
- index readiness and fingerprint status
- Chroma openability
- Redis connectivity
- Ollama reachability

The CLI exits nonzero on unhealthy states and prints a readable report for local troubleshooting.

### 5. Live eval runner

A live eval runner was added through:

- `src/ragnos/evals.py`
- `evals.py`
- `evals/regression.jsonl`

Current eval behavior:

- validates runtime readiness
- loads a JSONL dataset
- runs questions against the live local stack
- checks answer content and refusal behavior
- reports per-case pass or fail
- exits nonzero if any case fails

This is meant for local regression checks against the running stack, not offline unit testing.

### 6. Compatibility surface preserved

The compatibility facade in:

- `src/ragnos/core.py`

was updated so phase 3 helpers remain available through older imports where needed.

This includes exports for:

- catalog types and helpers
- health report helpers
- citation structures and rendering helpers
- new command constants

## Operator Workflow After Phase 3

The recommended local workflow is now:

1. ensure Redis and Ollama are running
2. run a health check
3. ingest existing PDFs or upload PDFs from the chat UI
4. start Chainlit
5. use `/status` when readiness needs to be checked
6. use the eval runner when validating behavior changes

## Commands

### Start the app

```powershell
uv run chainlit run main.py
```

### Run incremental ingest

```powershell
uv run python ingest.py
```

Optional overrides:

```powershell
uv run python ingest.py --docs-dir ./documents --chroma-dir ./chroma_data
```

### Run the healthcheck

```powershell
uv run python healthcheck.py
```

### Run live evals

```powershell
uv run python evals.py --dataset evals/regression.jsonl
```

```powershell
uv run python healthcheck.py --help

```


### 4. Manual health and readiness validation

Run:

```powershell
uv run python healthcheck.py
```

Expected checks:

- prompt file is valid
- docs directory exists
- fingerprint and index state are coherent
- Chroma can be opened
- Redis responds
- Ollama is reachable

### 5. Manual incremental ingest validation

Suggested manual check:

1. place one or more PDFs in `documents/`
2. run `uv run python ingest.py`
3. run it again without changing files
4. confirm the second run is effectively a no-op
5. modify or replace one PDF
6. rerun ingest
7. confirm only the changed file is reindexed
8. delete one PDF
9. rerun ingest
10. confirm deleted chunks are removed

### 6. Manual upload flow validation

Suggested manual check:

1. start the app with `uv run chainlit run main.py`
2. if no corpus is ready, upload PDFs through the startup prompt
3. ask a question from the uploaded content
4. upload another PDF through `/upload`
5. ask a new question that depends on the new document
6. run `/status`
7. confirm the app reports a healthy ready state

### 7. Manual citation validation

Suggested manual check:

1. ask a question that is clearly answerable from the corpus
2. confirm the answer ends with a `Sources:` section
3. ask the same question again
4. confirm the cached answer preserves the same sources block

### 8. Manual eval validation

Run:

```powershell
uv run python evals.py --dataset evals/regression.jsonl
```

Expected result:

- each case prints pass or fail
- the final summary reports totals
- the process exits nonzero if any case fails

## Known Boundaries

Phase 3 intentionally does not include:

- multi-user document isolation
- upload queues or background jobs
- RBAC or authentication
- HTTP health endpoints
- model-generated inline citations

The implementation remains local-first and operator-oriented.

## Recommended Next Checks

Before changing retrieval or prompting again, the safest routine is:

1. `uv run python healthcheck.py`
2. `uv run python ingest.py`
3. `uv run python evals.py --dataset evals/regression.jsonl`
4. `uv run python benchmark.py --question "..." --repetitions 3`

This gives a practical signal on readiness, corpus freshness, behavior regression, and latency.
